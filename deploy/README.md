# Выкладка на сервер

Сейчас бот крутится на `developer@77.216.6.4` (хост `redstar` в `~/.ssh/config`)
**без sudo и без Docker** — службами `systemd --user`. `Linger=yes` у
пользователя `developer`, поэтому всё поднимается само после перезагрузки
сервера, а упавший процесс перезапускается через 5 секунд.

⚠ На этом же сервере работает VPN-нода (контейнер `remnanode`, порты 443, 2083,
2096, 2222). Свопа нет, поэтому бот ограничен по памяти и процессору жёстче
служб из репозитория: см. «Лимиты» ниже.

До 27.11.2026 бот жил на `dev@109.199.115.142`. Там службы замаскированы
(`systemctl --user mask`), а данные оставлены на случай отката. Два сервера с
одним токеном одновременно запускать нельзя.

## Обновить

Само: push в `main` → GitHub Actions (`.github/workflows/deploy.yml`) гоняет
pytest и проверку типов рендера, затем запускает `deploy/update.sh`. Красные
тесты до сервера не доезжают. Две выкладки подряд встают в очередь, а не
обрывают друг друга. Запустить руками без коммита — Actions → deploy → Run workflow.

Для этого в репозитории нужен секрет `DEPLOY_SSH_KEY` — закрытый ключ, чья
открытая часть (`github-actions-deploy`, отпечаток
`SHA256:8Wk4yw5L…YYd1PZ4`) лежит в `authorized_keys` у `developer`. Проверено
27.11.2026: с одним ключом `github-actions-reelbot-deploy` выкладка падала на
`Permission denied (publickey)`. Ключ хоста сервера закреплён в `deploy/known_hosts`; сменится ключ хоста —
обновить этот файл, иначе выкладка честно упадёт на проверке.

Вручную, с машины разработчика:

```
deploy/update.sh
```

Код → зависимости (если менялись) → миграции → перезапуск → проверка, что все
службы живы (иначе скрипт выходит с ошибкой). Локальный бот на том же токене в
это время должен быть выключен.

⚠ rsync идёт с `--delete`: файл на сервере в `~/reelbot`, которого нет в git,
будет удалён. Свои бэкапы и данные держать в `~/reelbot-runtime`.

## Что где на сервере

| что | где |
|---|---|
| код | `~/reelbot` (rsync, без `.env`) |
| настройки | `~/reelbot/.env` (права 600), исходник паролей — `~/reelbot/deploy/.env` |
| Python, ffmpeg, cloudflared, uv | `~/reelbot-runtime/{venv,bin}` |
| Postgres 16 и Redis 7 | распакованы из пакетов Ubuntu в `~/reelbot-runtime/sys`, данные — `pgdata`, `redis` |
| ролики и исходники | `~/reelbot-runtime/storage` (`STORAGE_BACKEND=local`, MinIO не нужен) |
| модель распознавания | `~/reelbot-runtime/hf` |
| службы | `~/.config/systemd/user/reelbot-*.service` (копии из `deploy/systemd/`) |

Порты только на `127.0.0.1`: Postgres 5439, Redis 6390, Mini App 8099. Наружу
приложение выходит через cloudflared-туннель. Его держит отдельная служба
`reelbot-tunnel`: выкладка её не перезапускает, поэтому адрес приложения
переживает выкладку. Адрес лежит в `~/reelbot-runtime/tunnel.url`; бот читает
его на старте и вешает на кнопку меню. Новый адрес появляется, только когда
перезапущена сама служба туннеля (упал cloudflared, перезагрузка сервера,
`systemctl --user restart reelbot-tunnel`) — бот это замечает, перезапускается
и перевешивает кнопки.

Лимиты, чтобы не мешать соседям. В службах из репозитория: бот — 1 ядро и
768 МБ, Postgres 512 МБ, Redis 256 МБ. Поверх них на сервере лежат дополнения
`~/.config/systemd/user/reelbot-*.service.d/limits.conf` (выкладка их не
трогает): у воркера, бота и туннеля квоты процессора нет, воркеру отдано 4 ГБ,
`RENDER_CONCURRENCY=2`, `WHISPER_CPU_THREADS=4`; у всех служб `OOMScoreAdjust`
выше, чем у VPN-ноды, чтобы при нехватке памяти ядро снимало бота, а не её.
Больше двух потоков рендера здесь медленнее (замер 27.11.2026, ролик 17 с без
LLM: 2 потока — 388–416 с всего, 4 — 437 с, 3 — 468 с).

Там же `OUTPUT_FPS=0`: ролик выходит с частотой съёмки (30 → 30, 60 → 60).
При повторе кадров до 60 каждый кадр съёмки стоит ровно два кадра (замер меткой
яркости 27.11.2026): человек двигается с частотой съёмки, а камера и графика —
с частотой 60, отсюда рывки, а рендер вдвое длиннее. Замер на клипе 12 с:
частота съёмки — 189 с, повтор до 60 — 314 с, дорисовка
(`FPS_INTERPOLATION=motion`) — 520 с, ~20 с на секунду ролика; лёгкие настройки
minterpolate не быстрее (`obmc` −15 %, `hexbs` вдвое медленнее). Под дорисовкой
сервер перезагрузили (27.11.2026, 09:04 UTC) — здесь её не включать.

У воркера `CPUWeight=20`, `IOWeight=20`, `Nice=10`: свободный процессор весь
его, но при споре VPN-нода получает процессор первой.

В `~/reelbot/.env` на сервере (его видят и бот, и воркер): `OUTPUT_FPS=0`,
`RENDER_GL=angle` (рендер на четверть быстрее swangle, замер в комментарии к
`render_gl` в `src/core/config.py`) и `INTERMEDIATE_PRESET=superfast` (нарезка
и кроп быстрее; `ultrafast` ещё быстрее, но готовый файл от него на 15 %
крупнее). Окружение службы сильнее `.env`: то, что задано в `limits.conf`,
перекрывает его.

Что это дало, один и тот же ролик 28 с без LLM (27.11.2026): было 335 с
(нарезка 35, кроп 40, рендер 226), стало 274 с (23, 33, 177). С дорисовкой
кадров до 60, которая стояла утром, тот же ролик занял бы около 20 минут.

⚠ Бот отдаёт ролик в Telegram файлом, облачный Bot API принимает до 50 МБ.
Ролик 52 с весит 33 МБ, то есть всё длиннее ~75 секунд в чат не уйдёт, хотя
`MAX_VIDEO_MINUTES` разрешает три минуты. Пока это не закрыто (потолок битрейта
для длинных роликов или свой `telegram-bot-api`), пресеты и crf, от которых
файл растёт, на сервере не включать.
